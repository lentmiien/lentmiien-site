# Lantern Commons v1.2 — development handoff

This feature branch builds on accepted v1.1 commit
`1889dd949e0e85dbce193fe5c4ac172f7c8110ae`. No merge, deployment, production read,
production configuration change or live provider action is part of this delivery.
Product/client revision is `1.2.0`; persisted world identity remains
`lantern-commons-v1`, schema version **1**.

## Delivered journeys and canonical sources

**Quest board**, immediately northwest of Mori in the square: approach, open,
Previous/Next, Report as done, Refresh. It calls `createDashboardData().load('tasks',
resolvePolicy(currentUser))` directly. Therefore it matches `/mypage/api/cards/tasks`:
name-owned `scheduleTask/Task` todo and tobuy records, `done:false`, available now or
starting within 14 days, three source limits **12 overdue / 12 due today / 16 other**,
then the same status/planning-date/ID order. It includes the same optional automatic
accounting reminders for the configured personal owner, including their unavailable
state. Those reminders open their canonical close-month review page; they cannot be
reported done. There is no second task store, expanded global list or independently
paginated task source. The board's page flipping is over exactly the dashboard result.

Both the existing My Page completion endpoint and Commons use
`services/scheduleTaskCompletion.js`. Completion has strict current-name owner and
`todo|tobuy` predicates. Its conditional update preserves the original completion
stamp under concurrent retries; pending reminder cleanup is retried safely. A missing,
foreign, ownerless, presence or concurrently deleted record does not report success.
Reminder-cleanup failures return an error; retry reconciles an already-completed task.
The legacy schedule toggle endpoint retains its existing behavior. Normal Site pages
continue to work.

**Lantern Hall** now has a real interior. Its Village chronicle shelf reads the existing
Commons runtime diagnostics: online count, lease ownership, save failure flag, revision,
last successful checkpoint. Site almanac uses a bounded subset of the same Mongo
`collStats` source as `/admin/database_usage`, via `databaseUsageService`:

| Display | Model / existing source | Meaning and window |
| --- | --- | --- |
| Chat5 conversations | `conversation5` | All retained conversation records |
| Chat5 messages | `chat5` | All retained message records |
| Knowledge records | `chat4_knowledge` | All retained knowledge records |
| Saved GPT images | `gpt_image_generation` | Saved image records, not unique generation jobs |
| Saved music outputs | `music_generation` | Saved output records, not provider queue jobs |

These are deliberately selected archive-size indicators, not fabricated job queues or
unique-user metrics. The existing admin database usage page is role-admin-only; this
adapter additionally requires `commons.operations.read`. No further metric permission
is needed for this selection. The service reads five fixed collections with 2-second
command limits; failures are per-metric `unavailable`, never zero, raw database errors,
or cached content. Each open/Refresh queries again and displays its read timestamp and
all-retained-records window. No background polling or cross-client cache exists.

**The Shelter** has water jars, food sacks/crates and an equipment chest. Each opens a
read-only household summary calculated by `buildEmergencyStockSnapshot`, the canonical
pure function used by `controllers/escontroller.loadEmergencyStockData` for
`/es/es_dashboard`. It reads bounded local `es_category` (200), `es_item` (2,000), and
`es_profile` (`key:'household'`) records. Missing profile/overflow fails visibly; no
maintenance, synchronization, shopping mutation or uploads run. The existing ES model
has a single site household, with no owner/household selector. Family eligibility means
membership of that existing household, never a client-selected or unrelated household.

Water remains **litres**, food remains canonical **person-meal capacity** (including its
existing paired-food logic), portable toilets remain **uses**, medication coverage
**days**. Individual non-pooled categories retain their canonical units. Durable stock
uses **inspection-ready amount**, rather than unverified physical quantity. Text shows
current / active milestone target / unit / percent / canonical status. Numeric ratios
are `round(current / target * 100, 1)` without capping: 60 / 45 L is 133.3%. Only the
visual progress bar caps at 100. Zero target, not applicable and unknown readiness show
`—`; they are not invented as full preparedness. The canonical dashboard's capped
category progress remains unchanged. Food/water pooled targets are shown at domain
level, not added to counts or kilograms from their contributing categories. Expired,
expiring-soon, inspection-due and review-due counts are canonical sanitized summaries.
The stock's existing profile date/time policy and milestone logic remain unchanged;
the panel reports read time in Tokyo. Quantities never enter world snapshots.

**Cottage diary** is visibly on the existing desk, accessible only inside one's own
cottage, near the desk. It stores plain text in `commonsdiaries`, independent of Life
Log, tasks, NPC context and world saves. Save is explicit; past dates can be read with a
date picker or 20-date keyset history. There is no delete API. Limits: 10,000 JavaScript
string code units, expected non-negative integer revision, ISO calendar date only.
Empty text may be saved intentionally.

Today uses the existing Commons `Asia/Tokyo` policy (UTC+09:00, no DST), never browser
time. The app checks before and after fresh authorization; the atomic Mongo update
pipeline independently compares its **database command's `$$NOW`** Tokyo date. If the
date differs, a deliberate invalid date conversion aborts the *entire* write, including
an upsert, and becomes `DAY_CHANGED`. Real Mongo tests cover this. A write accepted by
the database just before midnight may finish/acknowledge just after midnight; its
acceptance date is the database operation's timestamp, not network delivery time.
The operation has 2-second execution and majority write-concern timeouts. Keep app and
DB clocks synchronized; divergent clocks fail safely rather than permitting backdates.

Owner/date uniqueness plus revision compare-and-set rejects racing tabs and creation
races. Stale editors show a clear day-change or conflict error and retain the local
draft. Load today does not silently move text into a new date. Reload saved entry keeps
the conflicting draft separately for copying. Drafts live only in page memory; closing
or refreshing the page warns when unsaved content exists. Socket disconnect purges
visible data; same owner-session reconnect can restore drafts. A server-generated hash
of immutable account ID plus session ID prevents restoration after account/session
switch. No localStorage, server draft store, AI writing or cross-feature sync exists.

## Permissions and private transport

See [the full security contract](V1.2-SECURITY.md). Existing auth uses **lowercase**
`type_user` values (`family` is displayed as “Family” in Manage Users); arbitrary casing
is not normalized into authorization. The current shared capability evaluator does not
supply a blanket admin shortcut. Narrow identity checks precede sensitive access.

| Account | Core play | Diary read/write | Hall | Shelter |
| --- | --- | --- | --- | --- |
| admin | bundled | own only, bundled | bundled operations + current admin | only ID `5dd115006b7f671c2009709d` while still admin, plus `emergencystock` |
| family | explicit `commons.world.play` grant | own only, bundled | denied | bundled `commons.shelter.read` + `emergencystock` |
| user | explicit `commons.world.play` grant | own only, bundled | denied | denied |
| custom type | explicit play and diary grants | own only with both grants | denied | denied |

Quest read additionally requires the exact dashboard section policy (`scheduletask`
and `dashboard.account.read`); completion requires `schedule.task.complete`, bundled
for admin/family/user as in the existing My Page shortcut. Existing typed user/group
role assignments are used. Family/user core play does not require Chat5 or NPC talk.
Missing grants produce an access-unavailable message, not an empty imitation dataset.
No editable account name is involved in Shelter or diary ownership.

New finite HTTP endpoints under `/commons/api`:

| Method/path | Request | Additional boundary |
| --- | --- | --- |
| GET `/quests` | no query | near Quest board, dashboard policy |
| POST `/quests/done` | `{taskId}` | same, completion capability and canonical owner |
| GET `/diagnostics` | no query | near Hall chronicle shelf |
| GET `/statistics` | no query | near Hall almanac shelf |
| GET `/stock` | no query | near Shelter display, current narrow eligibility |
| GET `/diary` | optional `date` OR `before` | own cottage, near diary |
| POST `/diary` | `{date,text,revision}` | same, current-day write capability |

All require authenticated session, play, and `X-Commons-Connection`, a random ticket
from the current same-session `/commons` socket's `joined` response. Tokens are neither
persisted nor logged. HTTP reads/writes freshly reload the socket session/account,
validate capabilities/proximity before work and again before response. Writes use
shared `sessionCsrf` token + Origin checks. The existing socket action event now enters
Hall/Shelter and returns finite panel identifiers; it never carries task/stock/stat/diary
payloads. No new arbitrary socket event, room or broadcast API exists. Rate limit is
60 requests/account/minute, one in-flight private request per connection, 64KB body
limit, 2-second database work limits. Responses are private/no-store. Invalid JSON and
oversized bodies produce generic errors.

Three-second audits and five-second authority deadlines remain. Role/grant changes
close sensitive panels, eject restricted scenes to a safe public door, and block reads.
Takeover invalidates the old ticket before any delayed response can be delivered.
Restricted scene restoration always lands at its public exit before the first snapshot;
re-entry revalidates eligibility. Interiors are isolated views even for two eligible
players. Generic admin database viewer list/read/delete explicitly excludes
`commonsdiaries`; admin role cannot bypass diary privacy there either.

## Renderer-neutral scene preparation

`services/commons/scenes.js` defines restricted layouts, bounds, spawn and public exit
transforms, entities, ground footprints, labels, asset keys and content-panel adapters.
Only the authorized player's snapshot receives that scene definition. Public facade /
quest geometry and the cottage diary entity are in `public/commons/world.js`.

- Units: world coordinates are floating-point tiles; Canvas uses 32 CSS art pixels per
  tile before camera scaling. +x is east/right; +y is south/down. Positions mark ground
  contact, not sprite top-left. Interior local origins are their northwest corners.
- Facing: `up/right/down/left`. Future 3D mapping: `(world x, elevation, world y)` in
  metres with 1 tile = 1 metre; Y is elevation, Z increases south. Facing north is
  negative Z, east positive X, south positive Z, west negative X. For a north-facing
  model, yaw is 0, π/2, π, -π/2 radians respectively (clockwise viewed from above).
- Collision uses explicit ground rectangles/ellipses; elevated visual silhouettes are
  separate. `visual` describes width/anchor; `asset` is a semantic reference. Sprite
  source rectangles/alpha reside in `CommonsWorld.art`, not simulation state.
- Scene spawn/exit transforms are authoritative. Local scene transforms are not global
  village coordinates. Cottage exit remains tied to the owner's immutable plot.
- The simulation consumes definitions and input; Canvas consumes snapshots. Future
  renderer adapters may resolve the same assets to meshes, labels to billboards, and
  panels to UI overlays without gaining authority over movement or eligibility.
- Static layout/art is distinct from private dynamic panel data. Do not copy panel
  quantities, tasks, diary text or aggregate replies into public scene snapshots,
  asset metadata, shared caches or NPC prompts. Interior fullness art is illustrative;
  accurate dynamic readiness is textual in the authorized panel.

No 3D renderer, model loader, glTF pipeline, physics library, runtime dependency,
framework rewrite or asset-generation service was added. Interiors retain cottage-style
fit-to-screen scaling; village zoom remains adjustable. The future 3D implementation
must preserve these authorization/data boundaries, mobile budgets and safe exits.

## Setup and later release (not performed)

1. Human test and approve this feature branch first. Follow feature → dev → main;
   nothing in this document authorizes a merge or deployment now.
2. No new environment variable, provider, dependency or infrastructure is required.
   Retain the v1.1 single-worker/session/Origin/lease requirements. Configure existing
   capability assignments above through normal Site role management.
3. `CommonsDiary` is registered in `database.js`. Normal Mongoose initialization creates
   its **unique `{ownerId:1,date:-1}` index**. The save service awaits `model.init()` before
   any write. In installations explicitly disabling automatic indexing, create the
   schema index using the normal reviewed model `createIndexes()` process before enabling
   v1.2; do not use destructive `syncIndexes()` or change existing world identity.
   The local real-Mongo tests verify BSON ID casting and the actual unique index.
4. Retain private Mongo backups. Diary entries do not expire automatically; authorized
   account-data removal must include that owner's `commonsdiaries` records through an
   offline reviewed operation. No generic admin browser access or deletion is allowed.
5. Cache only public static art/code as before. `/commons/api/*` is never edge-cacheable.
   Production logger categories include `commons.private`, `commons.statistics` and the
   existing auth/lease/persistence categories. No diary text, task titles, quantities,
   tickets or raw database errors are logged by the new adapters.
6. To roll back to v1.1, first move any saved `hall`/`shelter` resident transforms to the
   documented public exits and checkpoint using v1.2 under the normal release process;
   v1.1 intentionally rejects unknown scene names. Alternatively disable Commons while
   retaining all world/diary data until a reviewed restoration. Never delete or relabel
   `lantern-commons-v1` as a routine rollback.
