# Two-factor authentication

Authenticator apps supply a six-digit time-based code (TOTP). Administrators must enroll before gaining access; other supported account roles may opt in from User settings. The password step creates only a short-lived pending session until enrollment/verification completes. Existing admin sessions must sign in again on rollout. Recovery codes provide a second-factor alternative when the authenticator is unavailable.

## Security contract

- Zone/principals: logged-in, including a restricted password-verified enrollment/challenge principal; admin, family, user, other; no machine principals. Public login only establishes the restricted principal. API/service credentials retain their existing independent authorization.
- Classification: secret authenticator keys, recovery codes and trusted-browser credentials. Private account identifiers and enrollment state.
- Capabilities: `account.security.manage` assigned explicitly to admin, family, user, other; custom roles require a grant. Management is owner-only, with no admin override. Admins cannot disable their own second factor, even by submitting a forged request.
- Browser mutations: POST and shared CSRF on login, enrollment, confirmation, recovery-code replacement, disabling and cancellation. Pending sessions expire after 10 minutes and are bound to account ID, current password fingerprint, and factor version. Password verification alone never creates a Passport authenticated session for accounts requiring 2FA.
- Limits: login bodies 4 KiB; factor bodies 4 KiB/four fields; allowlisted inputs; six-digit codes or 32-hex-character recovery codes, password at most 1,024 bytes. Per-account factor mutations limited to 10 per 15 minutes, and page reads to 60 per minute; IP preauthorization limits also apply. Rate limits are per application process, consistent with existing login limits.
- Cryptography: maintained OTPAuth implementation, SHA-1 TOTP/30 seconds/six digits with one adjacent time step allowed. Atomically advance the last accepted counter to prevent replay. Recovery codes contain 128 random bits, are stored only as account-bound SHA-256 hashes, and are atomically consumed once. Ten codes are shown once on setup/replacement, never persisted as plaintext in session or database.
- Secret storage: TOTP secrets and pending setup material encrypted with AES-256-GCM and context/account-bound associated data using `TWO_FACTOR_ENCRYPTION_KEY`. No private files or external providers. QR codes are generated locally. Secret pages are standalone without analytics, third-party assets or notification sockets; escaped Pug and local CSS only; private/no-store and no-referrer.
- Trusted browsers: a host-only HttpOnly/SameSite=Lax cookie contains an authenticated encrypted verification receipt, valid for a fixed 90 days from actual factor verification (not renewed by ordinary login). It is bound to account ID, password fingerprint and factor version. Secure cookies are required in production. Sessions carry the same bounded proof. A password change or reset invalidates old receipts and session proofs; the current password-change session enters a new challenge immediately. A new browser, erased cookie or expired receipt requires verification.
- Lifecycle: enrollment/reenrollment, recovery replacement and disabling rotate the factor version, invalidating prior browser/session trust. Factor management requires the current password and an existing factor when enabled. Enrollment is active only after a valid code for the new secret. Password reminders run after completed authentication. General HTTP access validates the proof before application routes; Socket.IO handshakes and private chat deliveries/events do too. Active base sockets recheck at most every 30 seconds; Commons uses its existing short authorization refresh window.
- Logs: actionable configuration/database/session failures only, with stable category and operation; no secrets, request bodies, QR payloads or personal fields. Generic responses on failure. Pending secrets expire with the short setup session; used/replaced recovery hashes are removed; remembered browser cookies expire after 90 days.
- Negative tests: anonymous/pending access, admin enforcement and promotion, missing capability, CSRF, malformed/oversized inputs, incorrect/replayed TOTP, one-time recovery, stale passwords/factor versions, expiry, cookie tampering, concurrency predicates, configuration/DB failures, admin-disable denial, HTTP and realtime bypass attempts.

## Deployment

Set `TWO_FACTOR_ENCRYPTION_KEY` to an independently generated 32-byte base64 secret in the server's secret manager/environment **before deployment**. Generate it securely with `openssl rand -base64 32`. Keep a protected backup alongside the database backup. Do not commit or paste it into logs. Missing/invalid configuration logs an error and fails closed for factor enrollment/verification and mandatory admin login; public pages remain available. Use HTTPS and maintain an accurate server clock.

This is an additive schema change; no database migration is required. Existing accounts start unenrolled. Admins enroll at their next login; password-only sessions cannot retain admin access. Non-admin users remain password-only until they enroll. Trusted browsers are not shared across browsers/devices, and clearing cookies removes trust. Sessions still have their existing shorter application lifetime, so ordinary login remains necessary even when no second-factor prompt is due.

Changing the encryption key without re-encrypting stored secrets makes enrolled authenticators unusable. Preserve this key across deployments. Recovery-code verification can recover account access with a correctly configured key; keep codes offline. If an admin loses both the authenticator and all recovery codes, server-operator intervention is required: after independently verifying ownership, clear that account's `two_factor` enrollment and rotate its version using a controlled database maintenance procedure, then have the owner log in and enroll again. No web-admin bypass or email-only reset is provided.

Run the focused two-factor, user-settings, password-reminder and realtime suites, then `npm test`. Use synthetic accounts for browser QA; never enroll real users or invalidate production credentials during tests.
