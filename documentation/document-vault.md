# Document vault

The logged-in tool at `/document-vault/` files one scan per page. Upload a batch in page order, choose its owner and viewers, then use Review to check the English transcription and metadata against the scan and original-language OCR. Each page has its own paper disposition. A kept page needs a year label, folder ID and group label. Marking paper for disposal retains the digital scan. A single page supplies its own group description. For a batch, Chat5 combines the page descriptions in order. Reviewers can correct the English group description. Changing a page description queues a fresh summary unless the reviewer supplies a group correction in the same review.

## Security and operation

In the archive, **Date and storage filters** can combine a text search with an inclusive document date range and any combination of year label, folder ID and group label. Each location field matches a whole label, ignoring case. On a filed page kept in storage, the owner and any named viewer with vault read access can use **Edit storage location** to correct its labels. Saving checks the page revision and takes effect immediately in search.

- Data is sensitive. Admin, family and user accounts receive `vault.documents.read`, `vault.documents.intake` (including assigning an existing owner and selecting viewers), and `vault.documents.review`. Only admins receive `vault.queue.resume` by default. The usual explicit account/group grants also apply.
- Scope is the batch's immutable account IDs. The owner and uploader handle intake. Filed pages are readable by the owner and named viewers. An uploader filing for someone else needs to be named as a viewer for ongoing access. Only the owner can redo a filed page. Administrators have no document override.
- Passport and the shared session CSRF check protect browser mutations. Private, no-store responses use local scripts and styles and escaped text. The vault has no public, webhook, socket or machine API.
- A batch accepts up to 12 single-frame JPEG, PNG or WebP scans, 8 MiB per scan, 32 MiB total and 32 megapixels per image. Retrying the same upload form and files returns the accepted batch. Uploads have admission and rate limits. Scans are decoded and validated at intake. Original bytes live in private MongoDB scan records. Only an authorized page can deliver them. Scans have server-assigned IDs. No disk paths are accepted.
- The internal worker rechecks the initiating account and batch scope. Transient OCR and Chat5 jobs live with the batch. The worker runs the OCR workspace's default extraction and Chat5's local Ollama inference, using fixed, configured gateway destinations. Page classification sends one image and its OCR. Group classification sends only the ordered page descriptions. No ordinary workspace preview, chat history, embeddings or model tools are needed. Output is schema-checked before the temporary job is removed in the same database write.
- The database has one execution slot across web processes. A five-result window covers OCR, page classification and group classification. Three failures in the latest five attempts pause dispatch until an authorized operator verifies the services and resumes. Interrupted calls with uncertain completion also require checking that both services are idle. Uploads and reviews remain available. Redo is explicit.
- Page classification and group summaries request separate JSON schemas through the private Chat5 gateway. The vault accepts a single valid object surrounded by prose or a Markdown fence and validates its fields before applying them.
- On a Chat5 validation failure, open the affected page’s **Processing controls** to inspect the latest failed reply and its reason. The vault saves up to 131,072 UTF-16 code units per page or group reply and labels clipped replies. A successful classification or summary clears its previous diagnostic. Reading failed replies requires review capability and management access to the page. Reading a failed group reply also requires access to every page in the group. The archive search excludes diagnostics. Shared logs record the job ID, stage and failure reason without reply text.
- Source scans, original OCR, English text, metadata and paper locations remain as the archive. To retry a page after OCR succeeded, choose **English classification only**. Back up the vault's MongoDB collections with the rest of the private database.
- Deployment uses the site's existing MongoDB, OCR gateway and Chat5 local gateway settings and defaults to `qwen3.8:27b`. Change `document_vault.chat5.model` in **Admin → App Settings** to another local gateway vision model. Both classification steps read the current value when they run. The new collections and indexes are additive. No data migration, new secret, public storage mount or proxy cache rule is required. Keep this path out of edge caches. Rolling back the application leaves the vault collections intact.
- Tests cover authorization, CSRF, scoped scan delivery and search, file validation, structured responses, independent review and disposal, job serialization and cleanup, pause/resume and recovery.

Run the standalone MongoDB integration coverage with `DOCUMENT_VAULT_TEST_MONGO_URI=mongodb://127.0.0.1:PORT/document_vault_test npm test -- tests/integration/documentVault.test.js --coverage=false`. The suite creates and drops a uniquely named test database and uses local HTTP fixtures for the two model services.

Review suggests the document year, the owner’s uppercase name as a folder prefix, and a group label of **Other**. With **Invoice** enabled, the suggested group is Q1–Q4 from the document month. Changing the date or Invoice switch updates untouched suggestions. Choose **Use Other** or type over any suggestion. Filed location corrections use the saved values.

Filed pages lock 90 elapsed days after their upload timestamp. This covers location edits, page redos and changes to a filed group description. Initial filing remains available for older uploads still awaiting their first review. If a new redo is unfinished at expiry, the vault restores its last filed data. A redo already in progress before this update has no such checkpoint; finish reviewing it within its original upload window. Insurance can continue processing a filed invoice independently after the lock.
