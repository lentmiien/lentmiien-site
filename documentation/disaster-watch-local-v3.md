# Local Disaster Watch v3

Security contract: logged-in; interactive admin and explicitly granted users; no machine HTTP principals. Public provider data plus private configured location; admin-managed fixed Asahi-ku scope, no request-selected objects or coordinates. Capabilities `disaster.local.read` and `disaster.sources.refresh`; admin gets both, family/user get neither by default. Existing /admin gate remains. Browser refresh is POST with shared session CSRF, one request/minute and ingestion concurrency guard. GETs are side-effect free, private/no-store, analytics disabled. No uploads; query parameters rejected on summary API; refresh body only CSRF. Escaped Pug/textContent, static allowlisted artwork. Coordinates/raw payloads never enter summary DTOs. Outbound providers remain ingestion-only; no generation at runtime. Operational failures use utils/logger without payloads. Fixed summary slots retain last known state; legacy history retention unchanged. Negative tests cover capabilities, CSRF, XSS, bounded reads and absent/stale local evidence.

## Behavior and boundaries

Both `/admin/disasters` and `/mypage/api/cards/disaster` consume `buildSummary`; `/admin/disasters/api/summary` exposes the same DTO behind the same read capability. Each summary read is one projected primary-key query, limited to six versioned slots with a 1.5-second server deadline (the shared account adapter uses its existing 2-second deadline). No archive counts, regex scope searches, aggregation, provider calls, generated art, or GET writes remain in these paths. Archive pages are separate, deadline-limited, projected, and capped at 20 pages; they explicitly describe historical reports across all areas.

The six slots are measured weather, forecast estimate, authoritative local warnings, latest measured local earthquake, latest relevant typhoon context, and ingestion health. Their `_id` values contain an opaque digest of the configured weather location; coordinates and location configuration never enter the DTO. Weather, proximity geometry, and record selection use the existing `DISASTER_WEATHER_LOCATION_NAME`, `DISASTER_WEATHER_LATITUDE`, and `DISASTER_WEATHER_LONGITUDE` settings through one module. The public label and JMA administrative areas remain Asahi-ku. No new secrets or environment variables are required.

- Weather: actual OpenWeather current values take precedence while fresh (60 minutes). A separate forecast slot prevents a future forecast point from blocking a later measured reading. Forecast estimates require a point within 90 minutes and a provider snapshot received within 60 minutes. OpenWeather forecast steps are three hours; precipitation is labelled with its period. Unknown day/night does not assume sunlight. Old values are visibly last-known/stale; response `fetchedAt` never substitutes for `observedAt`.
- Warnings: only VPWW53/54 municipality `Body.Warning` evidence for Yokohama North qualifies. Numeric codes are product-specific. Prefecture names, headlines, South, nearby prefectures and generic bulletin titles are excluded. A full local state replaces its predecessor by source report/control time, serial and correction rank. Cancellations remove local hazards, bulletin retractions make coverage unknown, and conflicting same-revision variants remain unknown until a newer revision. No-warnings requires local coverage younger than six hours plus a successful local-warning source check within 45 minutes, with no unresolved potentially current warning candidates. This deliberately becomes unavailable on quiet days when no fresh authoritative local bulletin is available; successful HTTP retrieval alone does not renew an old bulletin's freshness.
- Earthquakes: JMA city/station observations and P2Pquake local points are normalized to measured `0,1,2,3,4,5−,5+,6−,6+,7` or unknown. Distant earthquakes do not displace the latest local observation. Corrections/retractions of that local event can make its intensity unknown. Magnitude and nationwide maximum are secondary. Reports older than 24 hours are explicitly historical. Legacy archive records with unrepaired local intensity are labelled unknown rather than claiming zero.
- Typhoons: centres must retain their own validity time, lie in a window from three hours ago through 24 hours ahead, and pass an actual 900-km great-circle test. Latest reports older than 24 hours do not qualify. A later report moving the same storm away removes proximity context. Local probabilities require explicit North/Asahi area names and a valid time; global maximum probability never determines local severity. All normalized probability areas are retained. Fresh local wind advisories/warnings can label the typhoon context, without claiming the typhoon caused them. Unsupported area identities/time structures remain unknown. The compact panel shows the latest relevant storm, not a multi-storm tracker.

Weather has a separate concurrency guard and is scheduled alongside alert processing, so an active alert run cannot block the next weather tick. Current weather is saved before forecast fetching. The alert run flag is reset even if initial database state access fails. Failed summary writes are retried from stored records, and old parser records in feeds can be refreshed for all categories, not just typhoons. HTTP payloads are capped at 8 MiB. Operational errors and bootstrap caps are logged through the shared logger.

## Release and rollback instructions (operator actions; not performed here)

Prerequisites: use the repository's Volta Node pin (`24.20.0`), a reachable application MongoDB, the existing production environment and matching weather location settings, and a retained prior application/static artifact for rollback. Run operator commands from the new release directory. The script does not load dotenv itself: use `node --env-file=.env ...` as below, or omit `--env-file` when the process environment already supplies `MONGOOSE_URL` and the same location settings. No dependency changes, destructive migration, or new secrets are required. Existing `OPENWEATHER_API_KEY` is needed for measured current weather; without it the normal weather path uses Open-Meteo forecast estimates. `DISASTER_INGESTION_ENABLED=false` disables the whole scheduler; `DISASTER_WEATHER_ENABLED=false` disables weather polling.

1. Stage the new committed application and static assets together through the normal release process. If source index presence is uncertain, complete step 2 before activating the new process, since its scheduler starts immediately after database readiness. Do not run `npm start` just to test this change: its prestart is mutating. Direct `node app` also starts the database lifecycle and background services; it is not a read-only inspection command.
2. Existing indexes needed by bounded bootstrap are `disaster_alerts {category:1,reportAt:-1}` and `disaster_weather_observations {locationName:1,bucketStartAt:-1}`. The new `disaster_local_summaries` collection uses only MongoDB's built-in unique `_id` index; no secondary summary index or new archive index was added. Normal startup retains Mongoose's automatic collection/index initialization: it can create the summary collection (and thus its built-in `_id` index), and can build missing legacy schema indexes. It does not wait for all those indexes before ingestion. If an older environment lacks the source indexes, the following additive command creates them (it never drops indexes); the operator needs index-creation privileges:

   ```sh
   node --env-file=.env scripts/check-disaster-local.js --indexes
   ```

3. Optional offline bootstrap, after source indexes exist and before activating the new process if prepopulation is desired (also usable after activation or when the scheduler is disabled):

   ```sh
   node --env-file=.env scripts/check-disaster-local.js --bootstrap
   ```

   This needs source-read and summary-write privileges. It is idempotent and only reads stored source records/writes compact summaries. It does not start the application, fetch providers, or invoke ingestion/generation endpoints. It reads at most 200 records per category across five categories (1,000 total) from the last 72 hours, with a two-second deadline per source query, and one recent weather record matching name and coordinates. Required raw subtrees are re-normalized. Revisions prevent older candidates from displacing newer state. It does not set source health or fabricate observation timestamps. Its version/location completion marker records a cap hit; repeating the command does not continue past a completed capped bootstrap. An exception leaves the marker absent for retry. There is no overall wall-clock deadline across candidate processing and writes.
4. Activate the staged application and static assets together. With ingestion enabled, the scheduler runs immediately after database readiness, then every 15 minutes by default (`DISASTER_POLL_INTERVAL_MS` overrides this). That first run performs the same bootstrap if its marker is absent, then normal polling. Weather polling runs independently alongside alert work. Normal parser upgrades allow 80 detail fetches per run by default (`DISASTER_JMA_MAX_NEW_DETAILS_PER_RUN`); backlog can take multiple ticks. The warning-readiness follow-up prioritizes recent warning candidates before archive repair and checks local readiness independently of the global deferred total (see below). Fresh local warnings can recover on the first completed verified poll even with thousands of historical deferrals; more than 80 eligible candidates require further bounded polls. Relevant provider failures, unresolved warning entries, absent recent local evidence, or disabled polling still keep status unavailable. Even healthy quiet-day warnings expire after six hours. Watch `Local disaster bootstrap incomplete`, `Local disaster bootstrap candidate cap reached`, and feed errors in production logs.
5. Read-only index/query verification after summaries exist:

   ```sh
   node --env-file=.env scripts/check-disaster-local.js --check
   ```

   The corrected tool disables both `autoIndex` and `autoCreate` before importing its three models; it imports neither app/database startup nor ingestion. Successful `--check` performs only source index listing and summary query explanation, so it can use a MongoDB read-only principal with `listIndexes`/find/explain access. An error can append a local application log; this is database-read-only, not a promise of zero filesystem writes. The original `76994c7` script disabled only `autoIndex` and could issue `createCollection`: use the follow-up fix for read-only inspection.

   Expect `hasCollectionScan:false`, at most six returned/examined summary documents, and `_id_` index access. The command prints source index keys and execution counters, not the winning plan/index name; it does not automatically fail on bad counters or assert that required source indexes exist. Zero results alone do not prove successful bootstrap or freshness. This tool never prints coordinate or source payload values. Then open `/admin/disasters` and the `/mypage` card as an authorized user: confirm matching temperature, provider observation timestamp, freshness, and local warning list. Empty/stale coverage must say unavailable, not all-clear. GET reloads only stored data. A manual source refresh, if separately desired by the operator, requires its capability and CSRF and returns immediately with an accepted message; it was not invoked in production for this work.
6. Rollback: restore the prior application/static release through your normal process. Existing archive records remain compatible; the additive local-state fields and separate summary collection can be left in place. No collection/index deletion is required. The old code would restore its known slow and broad regional behavior, so rollback is an operational fallback rather than a data migration.

Cloudflare/private-response rules should continue to bypass caching for logged-in routes; static versioned illustrations may be publicly cached. No Cloudflare change is needed.

Lennart needs no role-document migration if his validated session principal has `_id`, a nonempty `name`, and `type_user: 'admin'`: both new capabilities are granted by code bundles, even without role documents. Family/user bundles grant neither. Explicit capability grants do not remove the existing admin-only dashboard/card gates. No production identity or role data was inspected during this handoff.

## Local warning readiness follow-up (postdeployment)

The reported deployed baseline `da21c926aecd6fbd0d64e3e0cde0de96d52d45d2` had fresh 19:58 UTC VPWW53 evidence for `1410011` (two advisories), but its 22:44 UTC poll deferred 7,478 entries during parser repair. The previous global `feedErrors === 0 && deferred === 0` gate hid those advisories. This follow-up was developed with synthetic data only; no production service, database, startup, or refresh was accessed. [Supplied live verification session](/codex/sessions/tool-session-346be7e0d22d34530af317d8d0ae419385b344bfcce71076908cb454c40a2324), [release handoff](/codex/sessions/tool-session-a7ff01818ddaa86deb9fe199791aa8ca8e5076e709ddcdeb19968508731d13bb).

JMA describes [short feeds as every-minute updates covering at least ten minutes, and long feeds as hourly updates covering several days](https://xml.kishou.go.jp/xmlpull.html). Its [FAQ describes approximately seven days in long feeds, without a retention guarantee](https://xml.kishou.go.jp/qanda.html). Thus, with the retained 15-minute polling schedule, **both `extra.xml` and `extra_l.xml` must succeed**. A long feed is not simply irrelevant history: its recent entries can fill gaps between short-feed polls. The system still cannot guarantee immediate delivery between polls or during provider publication delays.

The new ingestion policy:

- Read all configured feeds, merge duplicate detail URLs, then allocate the existing 80-detail-attempt budget. Failed attempts count toward the cap and do not abort other candidates. Deduplication means deferred counts now represent unique entries, not repeated appearances across feeds.
- Prioritize potential VPWW53/54 warning entries within the six-hour window, including entries with unknown product or timestamp. Kanagawa/Yokohama title/author hints only prioritize work; they never establish or exclude geographic coverage. Newest candidates within each priority precede older ones. Only then spend remaining requests on other categories and historical repair.
- Recent candidates require a `localWarningCheck` marker tied to the parser/readiness version, even if already seen with the current parser. Old category classifications and summary-seen flags cannot exempt them. Refresh resets the summary-write marker so a failed summary write is retried from stored evidence before readiness recovers.
- Only parsed authoritative municipality evidence can establish local coverage or exclude another region. Unknown products, missing or ambiguous municipality structures, unknown local statuses, and bodyless corrections/retractions remain unresolved. Existing report/control/serial ordering, conflict handling, and event-matching retraction rules remain in force. All unresolved potential warning entries in the six-hour window block readiness, including older entries within that window; this intentionally errs toward unknown rather than assuming an unparsed correction is harmless.
- Persist unresolved candidates across polls/restarts, including candidates that disappear from the short feed before entering the long feed. Store at most 512 candidates. Overflow blocks readiness for at least six hours and emits an actionable warning; it never silently drops uncertainty to produce clear. Dated pending entries age out with the same six-hour window; undated retained candidates remain unresolved until verified. Ordinary parser repair does not require a mass backfill or deletion of seen flags.
- Require fresh feed metadata as well as successful retrieval: short warning feeds at most 45 minutes old; hourly long feeds at most 105 minutes old (one update interval plus the existing 45-minute tolerance); no more than five minutes in the future. Missing configured short/long warning feeds cannot certify readiness. Failed earthquake-only feeds do not invalidate warning readiness, but retain their global error diagnostics. Unknown custom feed types fail conservatively on errors.
- Mark health unknown during a refresh, then persist the warning-specific result. Its source-check timestamp is the **start of the feed check**, not completion of potentially lengthy archive work. The existing six-hour authoritative bulletin coverage and 45-minute successful-poll rules remain unchanged. Neither bootstrap nor successful feed downloads alone renew bulletin validity. GETs still read at most six compact primary-key slots and perform no provider calls or repair.

Diagnostic interpretation (stored ingestion `counters`, also compactly represented in health):

| Diagnostic | Meaning / operator response |
| --- | --- |
| `deferred` | Unique details postponed by the shared cap across all categories/ages; nonzero alone does **not** invalidate local warnings. |
| `feedErrors` / `detailErrors` | Global transport/processing failures; details now have a separate counter rather than aborting and mislabeling an entire feed. Investigate logged failures. |
| `warningPending` | Unresolved potentially current warning candidates; includes capped, failed, structurally unknown and unverified parser-version entries. Must reach zero for readiness. |
| `warningFeedErrors` | Failed/stale warning-capable feeds. Must be zero. |
| `warningFeedsPresent` | Both configured short and long warning feeds are present. Must be true. |
| `warningPendingOverflow` | Persisted pending storage cap was exceeded. Must be false. |
| `warningReady` | Source checks passed with no unresolved warning candidates. Local coverage and valid-time freshness must independently pass before current advisories or all-clear appear. |
| `warningCheckedAt` | Feed-check start time; slow repair cannot falsely renew the 45-minute policy. |
| bootstrap `capped` | One-time archive bootstrap hit 200/category; independent of live warning readiness and not a reason to rerun a mass backfill. |

Deployment of this follow-up needs no dependency, environment, index, or destructive migration changes. The additive archive `localWarningCheck` and ingestion-state `warningPending`/`warningPendingOverflowUntil` fields initialize during normal polling. Keep the existing bootstrap marker; no reset or manual bulk reparse is needed. Activate the committed application through the usual deployment process, allow the immediate scheduled run to complete, then inspect the above counters and the dashboard/card. If all current candidates fit in 80 attempts, a successful first poll can restore the supplied two-advisory case despite 7,478 historical deferrals. Larger current sets need additional 15-minute ticks; provider failures, genuinely ambiguous evidence, a pending overflow, or expired local bulletins can still keep status unknown. Do not raise the cap to clear archive backlog merely to make local health green.

The existing `--check` command remains database-read-only and verifies indexes/query shape only; it does not print readiness counters. Use authorized read-only database inspection of `disaster_ingestion_states` counters for diagnostics and compare the warning display with current local evidence (the supplied two-advisory example is historical, not a prediction of warnings at deployment time). No `--indexes` rerun is needed if the prior deployment already verified them. Rolling back this follow-up restores the former global-deferred gate; additive fields can remain stored.

## Final multi-level municipality fix (readiness v2)

This supersedes the classification-upgrade download behavior described above. Supplied deployed baseline: `2f7049e5b49a18004c3ed879d2e840a144f4690d`. The [read-only diagnosis](/codex/sessions/tool-session-33bd2276084aa4881090921c893184b220ed7940e6d973136b5dadc46e133e33) identified six-digit grouped-region blocks being mistaken for seven-digit municipal blocks. The supplied 23:18 poll had 232 pending entries with stored archive bodies, including 156 cached false classifications. No production requests, database changes, startup or deployment were performed while implementing this fix.

The shared classifier accepts the exact `気象警報・注意報（市町村等）` type. Its explicit compatibility aliases are `市町村等`, `二次細分区域` and `気象警報・注意報（二次細分区域）`; these aliases are not claims that the reconstructed production fixtures use those labels. Only boundary whitespace is trimmed. Grouped-region types, unknown labels, historical ambiguous `二次細分区域等` labels and substrings do not establish municipal authority. JMA's [warning XML specification, section 3-2-4](https://xml.kishou.go.jp/20170216_jmaxml_info_1.pdf) distinguishes the municipal block from grouped regions and specifies empty warning `EventID`/`Serial` tags. JMA's [2009 terminology change](https://xml.kishou.go.jp/20091111_jmaxml_info.pdf) explains the historical secondary-subdivision ambiguity. Existing product/date-specific local codes remain unchanged; VPWW54 remains eligible.

All recognized municipal blocks must have nonempty items, seven-digit area codes and structured kinds/statuses. Complete nonlocal coverage resolves readiness without writing local all-clear or replacing the local warning slot. Parent-only, incomplete, malformed, unknown local state and ambiguous correction/retraction cases remain pending. Empty `EventID` never creates an event association: unresolved candidates block the source-health gate across polls and restarts, including after feed rollover. The same six-hour pending window, 512-entry overflow protection, revision/conflict ordering and 45-minute health freshness still apply.

Recovery happens automatically in the normal ingestion/background or authorized operator-refresh path:

- The marker becomes `jma-v3-local:warning-readiness-v2`; the actual parser version is unchanged. Current-parser stored bodies are reclassified without provider detail requests, even when their previous result was false or their summary marker was already current.
- Each poll selects metadata for at most **512 feed/persisted-pending identities**, with a projected indexed `dedupeKey` query and **2-second** server deadline. There is no archive-wide scan. Persisted pending candidates have priority; attempts rotate so failing candidates cannot permanently starve unattempted ones.
- At most **256 stored-body attempts** run per poll, with a **15-second** work budget checked between candidates. Each projected primary-key body read has a **1.5-second** deadline, each marker write **2 seconds**; existing summary writes retain their deadlines. The last in-flight candidate may finish after the work budget. Only warning metadata and required raw warning subtrees are selected. Stale classifications take priority; current-version false results are eligible for stored-body retry after **15 minutes**. Unchanged unresolved results do not repeatedly log the same warning.
- Readiness markers are saved only after summary processing succeeds. Failed reads/writes and capped/deadline-deferred candidates stay pending and retry on later polls. A stale success marker cannot certify readiness. Real parser upgrades and missing records still use provider detail requests, with a hard maximum of **80 attempts**, including failures; the existing environment setting can lower this limit.
- GET behavior is unchanged: one projected read of at most **six compact slots**, no writes, provider calls or reclassification.

New diagnostics in ingestion counters and compact health:

| Field | Meaning |
| --- | --- |
| `warningReclassified` | Stored-body attempts this poll, including processing failures; at most 256. |
| `warningReclassifyDeferred` | Eligible selected cached candidates postponed by the count/time budget. Candidates outside the 512-identity selection remain covered by `warningPending`. |
| `warningReclassifyErrors` | Cached metadata/body/summary/marker processing failures; investigate the corresponding warning logs. |
| `localWarningCheck.reason` / `checkedAt` | Fixed classification reason and last successful stored classification time. Neither renews bulletin/report freshness. |
| log `bulletinId`, `reason`, `version` | Public JMA filename only, fixed diagnostic reason and classification version on unresolved classification logs; failure logs include filename when available and a fixed processing reason. No full URL, query string, title or raw body is logged. |

Expected first normal poll: the supplied 232 pending bodies plus the local bulletin fit within the 256-attempt limit. If all parsers are current, they require **zero additional detail downloads** for classification. If the 76 old records need actual parser repair, they use up to 76 of the unchanged 80-request budget; the 156 current-parser false results are repaired from storage. Under the time budget, successful feeds and database operations can therefore restore fresh local coverage in the first completed poll despite thousands of historical deferrals. A slower database, additional arrivals, actual unknown evidence or provider failures require further bounded ticks; readiness stays false until all relevant uncertainty clears. The supplied 23:07 local fixture has active thunder (14) and strong-wind (15) advisories with fog (20) cancelled, but deployment must use then-current evidence and the existing freshness rules.

**No extra operator command, bootstrap reset, bulk reparse, index migration, configuration change or backlog-cap increase is required.** Keep the existing bootstrap marker and allow normal scheduled polling. Use existing authorized read-only counters/log inspection if recovery does not complete; `--check` remains read-only and does not trigger classification. Rolling back to the supplied baseline reintroduces its classifier/download behavior; additive markers and pending fields may remain stored.

Regression fixtures in `tests/fixtures/jma/reconstructedWarnings.js` are explicitly **reconstructed, not downloaded originals**. They preserve the supplied filenames/times, 6+25 Akita hierarchy (VPWW53 and VPWW54), 7+54 Chiba hierarchy, 7+35 Kanagawa hierarchy, empty EventID and local hazard statuses. Unspecified municipality names/codes are synthetic. Tests cover both 232-record version mixtures with 7,000 historical entries, 256-attempt catchup, deadlines, retry rotation, summary/marker/lookup failure, pending retention, empty-ID corrections, duplicates/order/conflicts, diagnostics and the unchanged six-record read.
