# TARIC deployment and operator runbook

Management URL: `/admin/taric`. API: `/api/taric/v1`. Read [the release/security plan](taric-assisted-pilot.md) first. This release does not initialize production data at startup and does not run `setup.js` on your behalf.

## Human production setup

Run commands from the deployed repository with `MONGOOSE_URL` supplied by the normal secure operator environment. The script deliberately does not load `.env` or import `app.js`. Never put the database URI or credentials in chat/logs/command examples.

Preview (no connection or writes):

```sh
node scripts/taric-tool.js --bootstrap
```

Explicit initialization, idempotent collections/indexes/settings, with the fixed tool owner:

```sh
node scripts/taric-tool.js --bootstrap --owner taric-tool --execute --allow-database-write
```

This creates the seven TARIC collections, named indexes, three control documents, and disabled initial settings. It also ensures `amiamiitems.gcode` uniqueness for safe evidence upserts. It never resets data or drops indexes. A duplicate existing gcode causes index creation to fail; investigate manually instead of deleting data. Rerunning preserves existing settings, credentials and benchmark versions. No credential is generated by the script.

Set `TARIC_GATEWAY_ORIGIN` to the trusted fixed Gateway origin and include that exact origin in comma-separated `TARIC_GATEWAY_ALLOWED_ORIGINS`. Set `TARIC_GATEWAY_TOKEN` in secret storage if the Gateway requires it. There is no default origin or inheritance from the old Gateway wrapper. HTTPS is preferred; HTTP is permitted only for the operator-selected private LAN endpoint. Keep `/api/taric/v1` and `/admin/taric` uncached in Cloudflare/reverse-proxy rules; application authentication remains required with or without WAF/Access. Preserve Authorization, Idempotency-Key and CSRF headers. Do not enable request-body/header logging.

Deploy/start the application through the established operator workflow, respecting the known `npm start` prestart side effects. The TARIC worker starts with database readiness. No application was started against a real configured environment in development.

## Transfer and import private v0

The development source is the user-owned cleaned CSV; it is not in git and production has a different filesystem. Transfer it privately through the usual secure operator channel to a private location, for example `/secure/imports/taric-v0.csv`, readable by the import operator and outside `public/`. Verify:

```sh
sha256sum /secure/imports/taric-v0.csv
node scripts/taric-tool.js --file /secure/imports/taric-v0.csv --version 0
```

Expected SHA-256 `799e95dcce447381ca49aeaae65fb7937896971e0d3f943d12c40996b9f51ef8`; 55,373 bytes; headers `descriptive_name,full_item_name,specs,hs_code,taric_code,description,taric_description,description_summary`; 67 rows/accepted; 0 duplicate/invalid; 53 distinct target codes. The report includes template provenance and hashes only, not rows or prompts.

Import explicitly:

```sh
node scripts/taric-tool.js --file /secure/imports/taric-v0.csv --version 0 --execute --allow-database-write
```

Alternatively, sign in at `/admin/taric`, choose the CSV, keep version 0, review the displayed diagnostic policy, click **Preview hash and validation**, then **Import immutable draft**. Browser upload is bounded to 2 MiB and requires the shared CSRF token. Import populates a non-authoritative test catalog. It does not publish or enable normal mode. v0 can be run as a draft for diagnostics, or explicitly published; it is always ineligible for normal release.

Production must receive the source file through an operator transfer, not through a committed fixture. Remove the temporary transfer file under your private-data retention policy after verifying the import and backup. Gateway dataset download or changes are unnecessary.

## Enable and issue a unique key

At `/admin/taric`, an account with `taric.tool.manage` can enable the tool, leave catalog `null`, runtime `{"adapters":[]}`, and keep 256 output tokens. Initially only test calls can work; missing runtime metadata does not block the explicitly untested baseline.

Choose **Create / rotate key**. The 32-byte random secret is returned once, shown only on that page, cleared after 60 seconds or navigation, and never stored in the session or recoverably in Mongo. Copy directly into the external caller's secure secret store. If lost, rotate again. Expiry is 90 days. Rotation revokes the previous generation, queued jobs and old result read/replay authority; final feedback remains writable by the same stable integration after rotation. **Revoke key** disables all machine access. Clearing **Enable tool** is the inference kill switch; in-flight remote work may finish but its result cannot pass current checks.

No integration secret has been generated or printed by development tools. Do not paste a real one into docs, shell history, tickets or API debug logs.

## Exact machine requests

The following examples use placeholders, never a live credential. Use a stored gcode or a unique stored JAN in the caller; these synthetic examples are not seeded items.

```sh
curl -i -X POST 'https://YOUR_HOST/api/taric/v1/requests' \
  -H 'Authorization: Bearer REPLACE_FROM_SECRET_STORE' \
  -H 'Idempotency-Key: synthetic-request-0001' \
  -H 'Content-Type: application/json' \
  --data '{"item_code":"SYNTHETIC-1","descriptive_name":"Synthetic toy","input_hs_code":"9503.00","test":true}'
```

Accepted requests return HTTP 202 with opaque `id`, `state`, `poll_url`, `feedback_url`, `manual_confirmation_required:true`, `baseline:"untested"`, and the pinned adapter. This is durable acceptance, not successful inference. Poll with the same bearer:

```sh
curl -i 'https://YOUR_HOST/api/taric/v1/requests/REQUEST_ID' \
  -H 'Authorization: Bearer REPLACE_FROM_SECRET_STORE'
```

202 means pending/running. 200 means terminal; inspect `state`, `result` and `error`. Only complete non-null results can be offered for human confirmation. No errors imply a usable suggestion. The description is model-generated, not an official tariff label. Unknown catalog outputs, malformed/truncated JSON, context limits and upstream challenges produce manual-safe errors; they never trigger a silent adapter or scraping fallback.

After the user selects a code:

```sh
curl -i -X POST 'https://YOUR_HOST/api/taric/v1/requests/REQUEST_ID/feedback' \
  -H 'Authorization: Bearer REPLACE_FROM_SECRET_STORE' \
  -H 'Idempotency-Key: synthetic-feedback-0001' \
  -H 'Content-Type: application/json' \
  --data '{"selected_code":"0000000001"}'
```

The server derives accepted/changed/manual; the client cannot assert verification or training approval. A terminal error ID supports manual feedback. Invalid inputs/auth failures have no persisted request ID. One final choice is immutable; retry identical feedback with the same key. Code syntax is ten ASCII digits; codes outside the current approved list remain unknown/unverified.

Repeat the first POST with a **new idempotency key** and `test:false` (or omit `test`). Before an independent release exists it returns HTTP 503 `RELEASE_CLOSED`, without source fetch/generation. Reusing the test idempotency key for normal mode is a 409 conflict. Global application API keys and sessions return 401 on this API. Normal calls never automatically fall back to test mode.

Recommended caller control flow (external application changes are a later task):

```text
keep existing same-JAN reuse unchanged
when existing workflow reaches manual selection:
  persist a random idempotency key and exact request payload for this attempt
  POST once; on network uncertainty/429/503 retry same payload/key with bounded backoff
  if accepted, save request ID and poll at 2-second intervals up to the UI's time budget
  if pending too long or any error/hold: continue manual selection
  if complete: display suggestion + model-generated description + manual-confirmation label
  user chooses selected_code; commit the external workflow independently
  if request ID exists:
    asynchronously submit selected_code with a separate persisted feedback key
    retry transient feedback errors with the same key; never block the external workflow
    if job still active (409), wait until terminal before recording manual feedback
  never change test mode on a retry and never replay cached results around a release hold
```

Duplicate headers, JSON keys, extra fields, numeric codes, malformed IDs, query keys, compression or oversized bodies are rejected. Rate limits include polling/replays. Interactive queue has 20 slots. If a call was interrupted with uncertain provider outcome, a *deliberate* new attempt needs a new key; the old job will not automatically repeat provider work. Requests, feedback and their idempotency records expire after 90 days, so do not treat keys as permanent beyond retention.

## Independent benchmarks and approved catalog

First collect independently labelled cases. Use the same CSV headers plus optional source/group/provenance columns. For v1+ provide review JSON in the UI or `--review-file`:

```json
{
  "targetsReviewed": true,
  "independent": true,
  "trainingExcluded": true,
  "provenance": "Describe actual source, label review, holdout and product-family audit",
  "reviewer": "Recorded reviewer identity",
  "sourceLineage": ["Independent source identifier"],
  "minExact": 1,
  "maxInvalid": 0
}
```

These fields are declarations requiring actual review; example text is not acceptable evidence. `minExact`/`maxInvalid` are fractions in [0,1], frozen at import. Defaults are operational safeguards, not a statistical quality claim. Source/group exact overlap checks are mandatory but not semantic near-duplicate detection. Renamed/copied v0 remains contaminated. No v1 placeholder is created by bootstrap.

Preview/import with `--file /secure/imports/independent-v1.csv --version 1 --review-file /secure/imports/review-v1.json`, adding `--execute --allow-database-write` only for import. Then explicitly publish the immutable draft in the UI. Publication must increase the current version. No drafts, partial/failed runs or perfect v0 results open the gate. Correct a dataset/policy by importing a new version.

Normal mode requires a separately approved versioned code catalog in Configuration:

```json
{
  "approved": true,
  "version": "OPERATOR_REVIEWED_VERSION",
  "source": "Recorded authoritative source",
  "date": "YYYY-MM-DD",
  "applicability": "Reviewed jurisdiction/date/product scope",
  "attestation": "Recorded approval and reviewer",
  "codes": ["0000000001"]
}
```

The synthetic code above is a schema example, not an approved tariff. Supply a real reviewed list. v0-derived codes must never be relabelled as authoritative merely to enable normal mode.

## Runtime verification metadata

Normal mode requires runtime configuration for every candidate adapter:

```json
{
  "adapters": [{
    "name": "EXACT_ADAPTER_NAME",
    "identity": "IMMUTABLE_ARTIFACT_IDENTITY",
    "verified": true,
    "trustSource": "Who verified the deployment/artifact and how",
    "deploymentRevision": "IMMUTABLE_ACTIVE_DEPLOYMENT_REVISION",
    "baseRevision": "IMMUTABLE_BASE_SNAPSHOT_REVISION",
    "tokenizerRevision": "IMMUTABLE_TOKENIZER_REVISION",
    "adapterSha256": "64_LOWERCASE_HEX_DIGITS",
    "validUntil": "2099-01-01T00:00:00Z"
  }]
}
```

Choose a realistic short verification expiry; the long date is only a schema illustration. Saving a verified entry performs read-only checks against the fixed trusted Gateway:

- `GET /qwen3-lora/model`: exact `deployment_revision`, `model_revision`, `tokenizer_revision`.
- `GET /qwen3-lora/adapters`: array or `{adapters:[...]}`, exact adapter name and `metadata.artifact_sha256`.

This implementation deliberately **does not invent these metadata values or assume the current Gateway exposes all of them**. If fields are absent or mismatched, normal mode stays closed. The separate Gateway work should provide verified immutable base/tokenizer revisions, active deployment revision, adapter artifact digest, and trusted metadata attestation under the documented field contract (or a separately reviewed transport mapping). No Gateway change is required for v0 import or unverified test mode. All normal generate calls re-observe the identity before and after the call; the trusted Gateway must truthfully identify the runtime executing the named adapter and prevent artifact replacement under a fixed digest/revision.

`content` in generation responses must contain the entire strict JSON output; optional `raw_content` must match exactly, and optional `adapter_name` must match the request. Unsupported envelopes fail safely. Historical base/tokenizer revisions are unresolved; testing never turns that uncertainty into a verified claim.

## Runs, cancellation and rollback

Use **Load adapter metadata**, select an adapter, enter the benchmark ID, and queue a run. Repeat for additional adapters (maximum eight active runs). Cases run sequentially with interactive priority between cases, a six-hour total deadline, all required cases in the denominator, and optional diagnostic lexical similarity. Each new run supersedes the previous run's release authority for that adapter/configuration immediately. Inspect run state/counts/fingerprint/results and the readiness winner/reason.

A timeout/transport failure during generation or recovery of an uncertain in-flight claim creates a durable inference hold. In Readiness, confirm the Gateway is actually idle, check the acknowledgement box, then choose **Clear inference hold**. Pending work cannot proceed until this explicit action. It does not cancel remote work.

**Cancel future cases / revoke completed run** sets a durable cancellation flag and removes eligibility immediately. A pending/in-flight run stops before future cases; cancellation does not claim remote GPU cancellation. A completed run remains an immutable result record but cannot qualify. Configuration, catalog, code/dependency or runtime changes invalidate scores and require rerunning the current benchmark. Publishing a later independent benchmark holds old normal results until new eligible scores exist. A draft does not affect current release.

For rollback, disable the tool and/or revoke its dedicated credential. Keep the external manual workflow. Do not force-select old runs or rewrite published labels. Restore code by the repository's reviewed release procedure; configuration fingerprints still require current matching scores. Retain private benchmark provenance/results for audit and delete only through an explicit operator backup/retention decision.

## Development verification

No live scrape/provider/training and no production initialization are part of this release implementation. Focused tests use synthetic inputs. Real unique indexes and concurrency are exercised only with an opt-in disposable Mongo URI matching `mongodb://127.0.0.1:PORT/taric_test_NAME`:

```sh
TARIC_TEST_MONGO_URL=mongodb://127.0.0.1:PORT/taric_test_release npm test -- tests/unit/taricToolMongo.test.js --coverage=false --runInBand
npm test -- tests/unit/taricProtocolV1.test.js tests/unit/taricTransport.test.js --coverage=false
npm run lint:openapi -- taric-assisted.v1.yaml
npm test
```

The opt-in suite drops only its explicitly named synthetic test database. Without the safe test URI it skips. Never use real credentials, CSV rows or an application/production DB in tests. Browser availability and any skipped live checks are reported with the release; software tests do not establish tariff accuracy.
