# TARIC history and reviewed candidate export

## Security contract

- Feature: private request/outcome history, explicit human label review, candidate export preparation.
- Zone: logged-in. Interactive principals: holders of `taric.tool.manage`; admin bundle only by default, no family/user default grant. Machine principals: none.
- Classification: private. Scope: explicitly admin-managed requests under the server's `taric_settings/tool.owner`, across integration and browser principals. Foreign owners are never joined, counted, reviewed or exported. No caller-selected owner. The existing semantic middleware and `adminPrincipal` both check current authority.
- Mutations: shared session CSRF header, POST, strict JSON; actor from session principal. Read-only GETs do not enqueue work or contact providers.
- Limits: 2,000 filtered live requests plus archived reviewed cases per configured owner, 2,000 related verified conflict peers, 32 MiB combined projected population, 50 rows/page, 100 revisions/request, 128 KiB canonical source JSON per revision, 2,000-character review note, 255-character approved description; 200 export rows, 8 MiB JSONL, 100 published independent benchmarks / 50,000 cases. Database reads and review CAS have 2-second server deadlines. Existing admin rate limit and a two-operation concurrency cap per application instance apply. Limit failures fail closed with an explicit explanation; no partial statistics or conflict scan.
- Rendering: escaped Pug and DOM textContent, no provider blobs/hidden reasoning/credentials, no analytics, local assets, existing admin CSP. Cache: private/no-store, no-referrer, nosniff, noindex.
- Storage: separate server-owned review/audit and immutable export documents in private MongoDB, no filesystem artifacts. Human verification authorizes private retention of canonical source snapshots until operator retirement/deletion; no new TTL. Existing unverified raw requests/outcomes still expire after 90 days. Verified snapshots bound to final immutable feedback remain accessible and exportable after raw expiry; proposal-only archives remain stale/ineligible. See retention/deletion policy below.
- Outbound services: none. Logging: shared logger, operation/status only; never facts, notes or output payloads. DB failures produce 503, never empty successful statistics.
- Negative tests: session/capability/CSRF, owner scope, unknown/operator parameters, bounds, stale revisions/source, unvalidated proposals, immutable feedback, snapshot mismatch and output field allowlists.
- Migration: idempotent history bootstrap ensures ten TARIC collections including reviews/exports; this fix adds only optional fields and indexes. No automatic data migration or verification, release gate, credential, benchmark, worker, provider or GCS changes. Cloudflare must not cache these paths. Rollback removes navigation/routes; retain audit collections.

## Semantics

Verification is a human label attestation, not official TARIC validation or training approval. Ten-digit syntax is checked; catalog membership is contextual only. Review defaults to final human feedback. Without feedback, an accepted model suggestion requires explicit target confirmation. A correction requires an existing target, a note/source and a separate confirmation. Rejected diagnostic proposals cannot supply the default target. Description approval is always separate, never inherited from a model.

Every review appends a revision using single-document CAS, binding a hash of allowlisted source inputs, factual evidence, outcome, proposal, provenance and source dates. Arrival of any feedback, even an agreeing code, makes an earlier review stale. Concurrent source changes are detected on subsequent reads; a saved review does not lock immutable request/outcome collections. Active requests cannot be reviewed. The current source hash and expected revision must match; audit history is never rewritten. A stale verified revision remains in the audit but is ineligible. Each verification now freezes the full allowlisted canonical source in that revision; subsequent revisions also retain their displayed source once a case has been verified. Model mutation guards prohibit replacing prior audit entries. At 100 revisions, the API returns `413 REVIEW_REVISION_LIMIT`; it never truncates audit. Repeating an explicit Verify is a new human attestation with a new timestamp/revision, not a no-op or automatic bulk approval.

Profile `reviewed-code-candidates/1` needs a current verified target, captured full item name, descriptive name, and six-digit original HS. Specifications are optional and missingness is preserved. Approved description is optional; missing description warns that the current adapter's mandatory-description formatter is still pending. These are source candidates, not trainer-ready Qwen/LoRA files.

Conflicts are checked against indexed related verified reviews even outside the requested base filters (plus a bounded fallback for legacy reviews without identity keys): active current verified labels disagreeing within a JAN group or exact normalized canonical input group are derived as needs-review and excluded. Same-JAN changed facts remain distinct dedupe records but share a split group; contradictions are conservatively blocked until a reviewer explicitly withdraws/corrects a label. No source-applicability override or semantic near-duplicate detector is claimed. Exact duplicate inputs choose the latest verification, then stable request ID. NFKC/case/whitespace normalization is only for identity; exported facts retain their exact source values. Published, uncontaminated, independent release-eligible benchmark overlap/source/group hashes are checked; v0 is not a holdout. Unknown identities/paraphrases still need human checks.

Selector `reviewed-selector/1`: newest verification first or balanced by TARIC (lexicographic code round-robin, newest inside each code); default limit 100 and per-code cap 20, maxima 200 and 100. These are bounded pilot defaults, not optimized training policy. No duplication, oversampling, fabricated classes, split assignment or augmentation.

Preview is read-only POST and returns a digest of the bounded base-filtered source population, related review/conflict peers, holdouts, filters, options and selection. Download POST recomputes and compares it, then repeats a population check before freezing those exact rows. A change returns 409 and requires a new preview. The manifest records its validation cutoff, source/review hashes, options, exclusion decisions, algorithm/profile and SHA-256 of the exact candidate JSONL lines. The first JSONL line is a `reviewed-taric-export/1` manifest, remaining lines are `reviewed-code-candidates/1` candidates. Each row includes the complete canonical `source` and `review` objects: the repository canonical JSON hash reproduces `sourceHash` and `reviewHash` without database joins. The source includes exact inputs, facts/missingness, accepted suggestion or rejected diagnostic, final feedback, source timestamps and captured provenance. `sourceStorage` distinguishes live requests from archived reviews. These are not ready-to-train Qwen CSV files. A single document stores the exact complete JSONL and its SHA-256; no transaction/replica set needed. The cutoff is the final observed snapshot, not a cross-collection transaction or promise that no later edits can occur. Subsequent reviews do not rewrite frozen exports.

History statistics and filters cover live requests and archived reviewed cases only, never benchmark attempts. A live request and its retained review count once. Cards separately report live requests and archived reviewed sources; archived feedback represents the final feedback captured at review, not live outcome-collection activity. All timestamps/date boundaries are UTC (date-to inclusive day). Feedback shares use final-feedback count as denominator; they are not model accuracy. Cursor is `(createdAt, request ID)` descending and requires the returned population `snapshot`; changes return 409 rather than silently paginating a different population. Statistics and preview/export use the same final filters, not just the page. Indexed UTC date/JAN/mode/request-status predicates apply before the 2,000-case check and lookups for both live and archived sources. Other derived filters apply after bounded classification. Limit errors instruct the operator to narrow dates/JAN/mode/status; a large related conflict group or legacy review population can still require retirement/scaling. Reads use bounded aggregate joins, not application N+1 queries. Request IDs are strings, including lookup predicates; live dates are BSON dates and snapshot dates are canonical UTC strings. Upstream application/run/revision is not persisted by the current schema and is shown as unknown.

## Operator bootstrap and verification

Windows, Node 24.20.0, from the Site repository (human operation only):

```powershell
node --env-file=.env scripts/taric-tool.js --bootstrap
node --env-file=.env scripts/taric-tool.js --bootstrap --execute --allow-database-write
```

Do not pass `--owner` for an existing installation. The second command retains the existing owner/settings. The TARIC bootstrap reports exactly **10 collections**: `taric_settings`, `taric_credentials`, `taric_benchmarks`, `taric_runs`, `taric_requests`, `taric_outcomes`, `taric_controls`, `taric_attempts`, `taric_reviews`, `taric_exports`. History originally added the last two to the prior eight; this fix adds **zero collections**. Bootstrap also ensures the existing `amiamiitems.gcode` index (outside those ten).

This fix adds three request indexes (`request_filter_input_jan`, `request_filter_input_test`, `request_filter_state`), four canonical review source indexes (`review_source_date`, `review_source_jan`, `review_source_mode`, `review_source_state`), `review_conflicts` on owner/status/identity keys, and `export_source_requests` on owner/request references. Existing chronology/uniqueness/90-day TTL indexes remain. Fields added: optional revision `source` in `latest` and `history`, review `identityKeys`, and immutable export `requests` for scoped purge discovery. Counts remain derived, with explicit `live`/`archived` statistics; no counters, TTL pins or cleanup workers are added.

Bootstrap is idempotent: no key rotation, v0 reimport, request rewrite, runtime configuration change or GPU-control reset. Existing settings/control `updatedAt` can be refreshed by their set-on-insert upserts; their state is preserved. Isolated Mongo regression executes bootstrap twice and checks credentials, settings, v0, current request and GPU control fields. No new dependencies, environment variables or capability grants; only existing `taric.tool.manage` holders may use these routes. The manager header links to `/admin/taric/history` (`views/admin_taric.pug`); this document is `documentation/taric-history.md`.

Restart the normal Site service after the approved deployment/index bootstrap. `models/taric_tool.js` is included in `services/taric/gate.js`’s implementation fingerprint; adding request indexes changes that fingerprint. Existing normal-mode qualifying runs therefore need legitimate requalification against the new fingerprint under the unchanged gate. Bootstrap does not queue a run, release a hold or touch a GPU. Do not use `npm start` as a smoke test: its prestart performs unrelated maintenance/synchronization. No production deployment was performed in this review.

Open `/admin/taric/history`. Check a real request's proposal versus final choice, facts/missingness and UTC times. Compare filters and feedback denominators. Explicitly verify a good final choice, reload and inspect audit. Verify an incomplete label and confirm candidate eligibility remains blocked. Test withdrawal/correction with a reason. Later, when authorized, preview both selectors, inspect conflicts/holdouts/missing-description warnings, then download and parse the private JSONL. Do not automatically verify records or download production data as part of deployment. Two tabs should produce 409 on stale review/save or preview/download after a change. Check keyboard navigation, narrow layout and both theme modes.

Stored adapter/fingerprint and normal-mode runtime identities are shown. Template renderer/hash and catalog version are read only from the referenced stored run configuration when present; test requests have no persisted run/template/catalog snapshot, so those fields remain explicitly absent rather than inferred from today's configuration.

## UI and training contract readback

The form offers `Verified label`, `Needs review / withdraw verification`, `Excluded`, and `Unreviewed`. Saving requires a review note and a separate checkbox confirming the exact verified target. Correction text is `This is a training-label correction; the original final human choice stays unchanged. My note identifies the reason/source.` Description input is `Independently approved short description (optional; blank means not approved)`. Opening a changed-feedback case defaults the target to that human feedback, not the predictor or the prior training correction. No default description approval or bulk verification occurs.

The outside-catalog warning says `Default/current target is outside or absent from the test catalog. A well-formed human-verified code is permitted; membership is not legal truth.` The 53-code training-derived catalog is not a legal validity boundary. Missing facts, rejected diagnostics, stale source and archived freshness warnings remain distinct. Null approved description permits this code-label candidate profile and reports formatter-pending; it does not satisfy a future mandatory-description training format.

## Retention, source freshness and operator deletion

- A human verification captures exact canonical source facts and provenance (not credentials, hidden reasoning, provider blobs or raw transport), target, separately approved description or null, reviewer/time/note, feedback ID/hash and source hash in a single atomic review revision. The 128 KiB source bound and 100-revision cap keep the document below Mongo's 16 MiB limit, including latest/audit copies. Oversize sources fail explicitly instead of dropping facts.
- A snapshot with final feedback bound at verification has a closed outcome: the API permits one immutable final outcome per request. Requests/outcome facts are immutable in normal operation; outcome expiry is later than parent request expiry. Once the parent expires, feedback API calls cannot find it. This is the retention proof for exporting the canonical archived source; it is not a claim that an expired raw source is currently being checked.
- Verification before feedback is provisional for retention. Any later feedback, including agreeing feedback, makes its live source hash stale. After raw deletion, a snapshot without its own final feedback ID/hash is **always stale/ineligible**, even if nobody observed the intervening feedback. Reads do not mutate the audit. Such an archive cannot be reverified through an expired parent; resolve/reverify against final feedback while the parent exists, or create a new factual request and explicitly review it. No automatic promotion or fabricated final choice occurs.
- Existing hash-only reviews from `edc5cc2` are not silently upgraded. Their live detail warns `legacy_review_has_no_retained_source_reverify_before_expiry`. Lennart must legitimately re-review intended long-term cases before expiry. Already expired facts cannot be reconstructed from hashes. Frozen exports remain their original artifacts.
- Unreviewed raw data keeps its original 90-day TTL. Snapshots exist only after explicit verification, and remain in the private audit even after Needs review, Excluded or Unreviewed removes future candidate eligibility. They do not become machine API/raw-history records. Missing full name/category/HS6 still blocks the candidate profile; a verified target never supplies missing input facts.
- Withdrawal does not rewrite previously frozen/downloaded exports. To retire a case, use Needs review/Excluded with a reason. To **physically purge** it, an authorized operator must quiesce all Site writers/requests first, record an external non-content deletion receipt (owner, request/export IDs, actor/time/reason), delete the exact owner-scoped parent request and final outcome, delete the exact owner/request review document (all snapshots/audit), then delete whole owner-scoped exports referencing that request via `taric_exports.requests`. Delete whole exports, never edit immutable JSONL/checksums. Pre-fix exports lack this index field and need a private operator inventory of their JSONL to identify affected export IDs. Apply the same policy to backups and downloaded copies; the application cannot recall downloads. If a case has exhausted 100 audit revisions, quiesce and purge/retire it through this operator process rather than resetting its counter. Resume only after scoped absence checks. There is no automatic purge or new deletion UI, and no tombstone retains facts after physical purge. Random request IDs are not reused; removing the parent prevents subsequent outcome writes.
